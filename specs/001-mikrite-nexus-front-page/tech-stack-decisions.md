# Tech Stack Decisions: Mikrite Nexus Front Page

**Status**: Discussed and agreed in conversation, 2026-10-15. Input for the planning phase (`/speckit-plan`). Not a spec; requirements live in `spec.md`.

## Goal

A single-page, static HTML + CSS front page for Nexus. It should look modern and not generic, be fast, and use no client-side JavaScript.

## Decided

| Area | Decision | Rationale |
|------|----------|-----------|
| Page type | One static `index.html` | Single page, no routing or backend needed |
| JavaScript | None | Speed; no interactivity requirement that needs it |
| Styling | Tailwind CSS v4 (CLI) + daisyUI v5 | Existing component/utility classes, customizable via `@theme` and daisyUI themes so it does not look generic |
| Styling build | Tailwind CLI, run locally; `--watch` during development, `--minify` for production output | Compiles only used classes into a small `style.css` |
| Web server | nginx | Chosen for the production Linux server |
| Local testing | Docker Desktop running `nginx:alpine` with `site/` mounted read-only | Runs the same server software as production; no nginx install on Windows |
| Deployment | Not yet decided. Start with manual copy to the server; GitHub Actions deferred | Keep scope small until the page exists |

## Considered and not chosen

- **Plain CSS with custom properties**: lightest and simplest, but the team wants existing component classes. Remains a fallback if the build tooling becomes overhead.
- **Pico.css / classless frameworks**: fast to look decent, but the result would look like the framework.
- **Bootstrap**: heavier bundle and the most recognizable look; hard to make non-generic.
- **Tailwind CDN script**: prototyping only, not for production.
- **WSL2 + native nginx for local testing**: closest to a Linux server, but more setup than Docker and Docker was chosen.
- **Native nginx for Windows**: not a Linux environment; config and process behavior differ.
- **Python `http.server` / live-reload dev servers**: fine for quick previews, but not nginx, so they hide server config differences.
- **Caddy instead of nginx**: simpler HTTPS, but nginx was chosen.

## Local development workflow

Terminal 1 (CSS build, leave running):

```bash
npx @tailwindcss/cli -i ./src/input.css -o ./site/style.css --watch
```

Terminal 2 (web server, leave running):

```bash
docker run --rm -p 8080:80 -v "${PWD}/site:/usr/share/nginx/html:ro" nginx:alpine
```

Open `http://localhost:8080`. Saving a file rebuilds the CSS; refresh the browser. The container reads from disk, so it does not need restarting.

## Planned project layout

```
src/input.css        Tailwind source: imports, daisyUI plugin, @theme tokens
site/index.html      The page (only folder served in production)
site/style.css       Generated by Tailwind; not hand-edited
package.json         Node tooling: tailwindcss, @tailwindcss/cli, daisyui
```

## Constraints to carry into planning

- No client-side JavaScript in the page itself.
- Only `site/` is served; repo specs and tooling stay out of the served output.
- Must work at phone width with no horizontal scroll.
- Respect `prefers-color-scheme` and `prefers-reduced-motion`.
- Keep total page weight small; the compiled CSS should be a few tens of KB at most.

## Open questions

- Brand palette, typography, and fonts (Google Fonts vs. self-hosted).
- Page content and sections.
- Production hosting details: server OS, domain name, HTTPS (Certbot is the usual choice with nginx).
- Deployment method: manual copy vs. GitHub Actions (SSH/rsync), to be decided after the page exists.
- Whether `dist`/built CSS is committed or generated at deploy time.

## Notes for the planning agent

- Treat "Decided" items as fixed unless the user changes them.
- Treat "Open questions" as items to surface to the user, not to assume.
- Favor the simplest option that meets the constraints; the user is aware that plain CSS would be lighter.
